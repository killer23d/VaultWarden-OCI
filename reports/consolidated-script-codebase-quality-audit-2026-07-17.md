4. Health locking should remain separate from the global mutating-operation lock.
5. Large cohesive safety-critical workflows should not be split solely to reduce line count.
6. Systemd installer cohorts should remain explicit boundary assertions rather than becoming a registry.

Correct `setup.sh --force` acknowledgement behavior and add focused regressions. It is a small operator-contract fix with no need to alter shared architecture.

## 7. Confirmed findings

### CQA-001 — `setup.sh --force` advertises alternatives but requires both acknowledgements

**Severity:** Medium  
**Evidence:** E2  
**Confidence:** High  
**Affected code:** `setup.sh:105-112`, `setup.sh:267-286`

The help text says an operator may set:

```text
VW_FORCE_ACK=I_UNDERSTAND_LOSING_OLD_BACKUPS
```

**or** answer the interactive prompt. The implementation exits with status `2` when the environment token is absent before the TTY prompt can be reached. An interactive operator must therefore provide the environment token and then type `YES`.

This fails safely, but the public destructive CLI contract is false and the advertised interactive path is impossible.

**Canonical owner:** `setup.sh`.

**Correction:**

- interactive TTY: allow the `YES` prompt as the acknowledgement alternative;
- non-interactive execution: require the exact environment token;
- preserve dry-run exemption;
- do not let `--force` bypass the operation guard.

**Required tests:**

- interactive missing token + `YES` succeeds past the gate;
- interactive `NO` or EOF/timeout refuses;
- non-interactive missing token exits `2`;
- non-interactive valid token proceeds;
- dry-run does not prompt or require the token.

### CQA-002 — Operation lock-file policy changes with source order

**Severity:** Medium  
**Evidence:** E2  
**Confidence:** High  
**Affected code:** `lib/common.sh:438-495`, `lib/operations.sh:166-181`, `utilities/setup-systemd.sh:443-490`

`lib/common.sh::_ensure_lock_file()` defines the intended lock-file preparation contract: root-owned, shared `vaultwarden` group where available, mode `0660`, pre-setup fallback, and actionable diagnostics.

`lib/operations.sh::_operation_try_lock_into()` uses that contract only when `_ensure_lock_file` happens to be defined. When operations is sourced without common, it independently creates the path and applies mode `0600`.

The shared operation subsystem therefore has two policies depending on source order. A standalone or differently ordered caller can create a root-only lock that later conflicts with the intended shared-group access model.

**Canonical owner:** `lib/operations.sh`.

**Correction:** move the narrow lock-file preparation implementation into `lib/operations.sh` and remove the optional fallback branch. Keep setup-systemd's explicit lock cohort as installation-time enforcement.

**Must preserve:**

- kernel `flock` as authority;
- no deletion based on lock-file age;
- existing contention and exit-`75` semantics;
- pre-setup root:root `0660` fallback when the group is unavailable;
- current installed-runtime lock cohort.

**Required tests:** source operations standalone and through normal source order; assert identical creation mode, ownership/fallback behavior, acquisition, and diagnostics.

### CQA-003 — Root enforcement has one ambiguous helper contract and multiple caller styles

**Severity:** Low  
**Evidence:** E2  
**Confidence:** High  
**Affected code:**

- `lib/common.sh:148-154`
- `startup.sh:121-125`
- `utilities/env-edit.sh:283-285`
- `utilities/setup-systemd.sh:706,1040,1137,1505`
- `utilities/setup-firewall.sh:546`
- `utilities/setup-system.sh:993`

`require_root()` always emits a generic error and appends all supplied arguments to a generated `sudo` command. Callers that pass an English sentence produce a misleading, non-executable remediation command.

Other scripts that already source common use inline `EUID` checks. These checks enforce root correctly, so this is not a privilege bypass; the defect is inconsistent operator diagnostics and unclear helper signature.

The larger report's suggested `require_root "custom message"` form must not be implemented because it repeats the current misuse.

**Canonical owner:** `lib/common.sh::require_root` and its direct callers.

**Correction:**

1. Document one signature: arguments are the original command arguments used in the remediation hint, not a custom message.
2. Correct prose callers to pass real CLI arguments or no arguments.
3. Only then redirect inline checks in scripts that have common available.
4. Keep early checks local where common is genuinely unavailable.
5. Preserve help/version paths before the root gate.

**Required tests:** non-root direct invocation must assert the exact hint for startup, environment sync, systemd setup, firewall setup, and system setup.

### CQA-004 — Dashboard `.env` parsing retains surrounding quotes

**Severity:** Low  
**Evidence:** E2  
**Confidence:** High  
**Affected code:** `dashboard.sh:32-54`, `lib/config.sh:104-120`, `utilities/env-edit.sh:118-127`

The canonical loader accepts surrounding single or double quotes and strips them. Dashboard's `_read_env_var()` returns the raw text after `=`.

For example:

```text
PROJECT_STATE_DIR="/var/lib/vaultwarden"
```

is loaded canonically as `/var/lib/vaultwarden`, while dashboard stores the quote characters and can perform checks against the wrong path.

**Canonical owner:** accepted environment value grammar in `lib/config.sh`.

**Correction:** make the dashboard's read-only parser strip one matching surrounding quote pair. Prefer a local correction unless a caller search proves a stable shared read-only helper can replace both dashboard and env-edit behavior without changing other callers.

**Required tests:** unquoted, single-quoted, double-quoted, empty, missing, and value-containing-`=` cases for state directory, backup directory, timezone, and rclone remote name.

### CQA-005 — `lib/docker.sh` computes Compose project identity at source time

**Severity:** Low  
**Evidence:** E2  
**Confidence:** Medium-high  
**Affected code:** `lib/docker.sh:38-56`

When `DOCKER_PROJECT_LABEL` is unset, sourcing the library immediately runs `docker compose config --format json` and derives a label from the caller's current Compose context. It may also print a warning while a caller is only sourcing helpers.

The earlier report overstated this as requiring a running Docker daemon. The verified defect is narrower:

- source-time external command execution;
- dependence on caller current directory and compose context;
- warning output in help/test/library-load paths;
- label selection before the owning Docker operation is known.

**Canonical owner:** `lib/docker.sh`.

**Correction:** defer project-label resolution to a small private function called by helpers that need the label. Preserve explicit `DOCKER_PROJECT_LABEL` overrides and the existing default label.

**Required tests:** source the library with no Docker command available, outside a Compose directory, with explicit override, and with a mocked Compose project name; sourcing alone must remain quiet and successful.

## 8. Strong risk requiring a design decision

### CQA-R01 — Recovery promotion is outside the shared operation guard

**Severity:** Medium risk  
**Evidence:** E3  
**Confidence:** Medium-high  
**Affected code:** `recover.sh:1-18`, `recover.sh:387-455`, `recover.sh:539-555`, `lib/operations.sh`

`recover.sh` performs a multi-artifact promotion before invoking guarded startup, but it does not source `lib/operations.sh` or acquire the shared mutating-operation guard.

The documented workflow targets a replacement host and automation is enabled after recovery. That lowers the expected likelihood of conflict, but the assumption is not enforced by the script.

**Trigger:** recovery is run on an initialized host while backup, environment sync, secrets/key work, setup/systemd work, or timer-managed mutation can overlap.

**Potential impact:** another process can observe or change a partially promoted recovery generation. Recovery's local rollback cannot undo the competing process.

**Bounded decision:** permit recovery on an initialized host and acquire the existing shared guard before backup/staging/promotion. This is simpler and more robust than building a broad offline-host detector. Keep the local recovery transaction unchanged.

**Required tests:**

- contention returns the established non-interactive status;
- recovery does not create/promote artifacts when guard acquisition fails;
- signal/rollback tests remain valid;
- operation status identifies recovery clearly;
- no systemd unit or new scheduler is introduced.

## 12. Intentional specialization

The following similar-looking implementations should remain separate:

1. **Backup tiers:** database, full, and emergency have different contents, key/protection requirements, verification, retention, and restore contracts.
2. **Restore versus recovery:** ordinary restore selects backup artifacts; `recover.sh` re-establishes operational identity from a surviving state volume and offline key.
3. **Recovery-local atomic writes:** local staging and rollback are part of one multi-file generation and should not be replaced by a generic transaction helper.
4. **CrowdSec email transaction:** commit markers and operator-owned configuration preservation are domain-specific.
5. **Logging descriptor cleanup:** keep local to `lib/log.sh`; do not force a dependency on operations.
6. **Health lock:** read-oriented health contention differs from global mutating-operation contention.
7. **Systemd cohorts:** explicit service, timer, writable-path, root, and lock lists are boundary assertions, not a reason to create a registry.
