You are working on https://github.com/killer23d/VaultWarden-OCI on branch delta.

Goal:
Recent changes introduced too many mixed privilege assumptions. Simplify the project to
a small-project, root-operated privilege contract so the stack becomes functional and
predictable again.

Primary contract:
- setup, startup, restart, stop, maintenance, backup, restore, secrets, systemd,
  firewall, DNS update, and runtime health checks are root-operated.
- `sudo make up` and `sudo make restart` must be valid supported commands.
- Runtime config/secrets/state are root-owned where appropriate:
  - /etc/vaultwarden: root:root, 0700
  - /etc/vaultwarden/vaultwarden.env: root:root, 0600
  - /etc/vaultwarden/age-key.txt: root:root, 0600
  - /run/vaultwarden-oci/secrets: root:root, 0700
  - decoded Docker secret files only under /run/vaultwarden-oci/secrets
  - ${PROJECT_STATE_DIR}/config/install.env: root:root, 0600
- Repo-local .env may remain as operator-editable source/fallback, but root startup
  must not keep chowning it back and forth.
- Do not loosen secret permissions to make non-root reads work.
- Do not redesign into an enterprise/dedicated service-user model.
- Do not weaken systemd hardening unless required for functionality and explicitly
  justified.
- Keep changes surgical and focused on making the existing stack work.

Required fixes:

1. Makefile root lifecycle
- Update ROOT_ALLOWED_TARGETS so `sudo make up`, `sudo make down`, `sudo make start`,
  `sudo make stop`, and `sudo make restart` are allowed.
- Consider allowing `sudo make health`, `sudo make status`, and `sudo make logs` if
  they need root-owned runtime files.
- Remove or revise comments/help text saying service lifecycle relies on the login user
  being in the docker group.
- Update help text and next-step messages from `make up` to `sudo make up` where this
  is the production/admin path.
- Keep developer/test targets non-root where appropriate.
- Make lifecycle targets root-required where appropriate. Non-root `make up`,
  `make down`, `make start`, `make stop`, and `make restart` should fail fast
  with a clear message such as: `Run: sudo make up`.

2. Startup root contract
- In startup.sh, require root early for real startup operations, except harmless
  --help, --version, and possibly --dry-run.
- Remove the auto-chown of repo .env to the real user from startup.sh
  load_environment().
- Do not tell operators to fix root startup by chowning .env to the current non-root
  user.
- Keep /run/vaultwarden-oci/secrets root:root 0700.
- Keep push placeholder files as root-owned and readable by containers as currently
  intended.

3. Stop auto-fixing repo .env ownership during startup
- In lib/common.sh, change auto_fix_critical_permissions() so it does not chown repo
  .env to the login user during root startup.
- If a repo .env permission helper is still useful, leave it only in
  `sudo make fix-permissions`, not in normal startup.
- Update stale warning text in get_real_user() that says "use sudo ./setup.sh, not
  sudo make setup" so it no longer contradicts the supported Makefile workflow.

4. Runtime environment ownership
- In utilities/setup-env.sh refresh_state_artifacts(), install
  ${PROJECT_STATE_DIR}/config/install.env as root:root 0600.
- Ensure ${PROJECT_STATE_DIR}/config exists with root-controlled permissions suitable
  for root/systemd runtime.
- Keep repo .env behavior simple: it may be written for operator editing, but the
  persistent runtime copy must be root-owned.
- setup-systemd.sh should continue installing /etc/vaultwarden/vaultwarden.env as
  root:root 0600.

5. Remove stale decoded-secret path usage
- Remove secrets/.docker_secrets from live startup, Makefile, health, and operator
  guidance paths.
- In Makefile up, do not hard-fail or rely on secrets/.docker_secrets/admin_token;
  startup.sh is responsible for decrypting secrets.yaml into
  /run/vaultwarden-oci/secrets.
- In utilities/maintenance-health.sh, check /run/vaultwarden-oci/secrets when
  checking decoded runtime secrets.
- Do not require a broad docs/changelog rewrite unless those references actively guide

6. Root health / maintenance compatibility

- For direct manual health invocation, choose one clear policy: either support

- Keep existing load_project_environment() behavior unless a small targeted fix is
